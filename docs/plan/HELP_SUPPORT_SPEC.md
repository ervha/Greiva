# ヘルプ・利用案内・問題解決 設計案 v0.1

更新: 2026-09-30。ユーザーの「ヘルプページやそれに類するものも作るよう設計して」という追加要求に基づく。本書は製品設計であり、ヘルプ画面や記事の実装済みを意味しない。具体的なUI、記事一覧、提供時期は後続の実装計画で確定する。

## 1. 目的と境界

利用者が「何ができるか」「どう操作するか」「うまくいかないときにどうするか」をアプリ内で調べ、元の作業へ戻れるようにする。初めての利用、機能の再確認、問題解決に同じ説明を使う。

`GREIVA_REQUIREMENTS.md`・`GREIVA_DESIGN_SPEC.md`のlocal-first、状態を偽装しない方針、アクセシビリティ、診断情報の扱いを引き継ぐ。Calendarの案内は`CALENDAR_TIMETABLE_SPEC.md`の汎用定期予定/時間割モデルと整合させる。PoC仕様・実装順序・Gateは変更しない。

## 2. 案内の種類

| 案内 | 利用する場面 | 内容・戻り先 |
| --- | --- | --- |
| ヘルプページ | 使い方を探す、全体を学ぶ | 検索、カテゴリ、FAQ、記事。前の画面へ戻れる |
| 文脈ヘルプ | 特定の画面・操作が分からない | その操作の説明を直接開き、元の作業位置へ戻る |
| 入力補助・Tooltip | 用語や項目の意味を確認する | 短い説明。詳細が必要なら対応記事へ進む |
| 初回案内・再学習 | 初めて利用する、使い方を思い出す | 短い手順。スキップ・閉じる・ヘルプから再表示 |
| 空状態の案内 | Pageや予定がまだない | 次にできる操作と基本ガイドへの入口 |
| エラー解決ガイド | 保存・同期・権限等の問題がある | 現在の状態、確認手順、実行可能な対処 |
| アプリ情報・診断 | 版を確認する、問題を報告する | アプリ版、環境、確認済み状態、診断情報のプレビュー |

基本の説明はヘルプ記事を共通の参照先とし、画面ごとに別の長文マニュアルを複製しない。入力の意味や重大なエラーはその場でも説明し、記事を開かないと意味が分からない状態にしない。

## 3. 情報構造と記事の設計案

```text
ヘルプ・アプリ情報
├─ ヘルプ内を検索
├─ はじめに
├─ ページと編集
├─ タスクと関連
├─ カレンダー・定期予定・時間割
├─ 保存・同期・オフライン
├─ ショートカットと操作方法
├─ よくある質問・問題解決
└─ アプリ情報・診断
```

記事カテゴリは提供されている機能に合わせる。将来設計中の機能を現在使える機能として案内しない。

| 対象 | 記事に含める内容の例 |
| --- | --- |
| はじめに | 基本の作業、画面の移動、保存状態の読み方、あとから案内を開く方法 |
| Page / Editor | 「/」候補、Mention、Toggleの開閉・本文移動、ブロック移動、Undo/Redo、keyboardとタッチの操作 |
| Task / Relation | 作成・完了・期日、関連を付ける/外す、削除と復元 |
| Calendar | 曜日と時間帯/自由な時刻、繰り返し期間、毎週/隔週、一回の取消・振替・追加、時間割と他用途の例 |
| 保存・同期 | 端末への保存と同期の違い、offlineで使える範囲、再接続、Conflictの解決 |
| FAQ / 問題解決 | 入力できない、予定が見えない、同期されない、保存エラー、権限エラー等 |
| アプリ情報 | アプリ版、platform、更新履歴への導線、診断情報の確認・書き出し |

記事は「できること」「前提」「操作手順」「操作後の確認」「関連する説明」を基本構成とする。手順は画面と同じ用語を使い、利用者向け本文にDB名や同期プロトコルの実装詳細を並べない。

Calendarでは「振替＝既存の一回の移動」「追加＝元の繰り返しを変えず一回増やす」を具体例で説明する。休講/中止、補講/追加開催など、用途が違っても同じ操作へ案内する。

定期予定の変更は「この回だけ／この回以降／全体」の違いと、過去の保持、休講・振替の引き継ぎ案の確認方法も説明する。振替先の日時を保つことと、対応先が不明な例外を個別に確認することはCalendarの設計に合わせる。

## 4. 検索・FAQ・ショートカット

- ヘルプ内の検索は同梱記事のタイトル・説明・本文・用語別名を対象とする。アプリのPage/Task全文検索や外部サービスに依存させない。
- 「休講」「中止」「取消」等の別名から同じ説明へ到達できる。完全一致のタイトルや用語、関連カテゴリが探しやすい順位とし、結果には短い説明を付ける。
- 結果なしでは入力文字を残し、語句の変更とカテゴリからの閲覧を案内する。外部への検索送信を自動で行わない。
- FAQは独立した矛盾する答えを持たず、基本記事の要点と対応記事へのリンクを使う。
- ショートカットはplatformと実際の機能提供状態に合わせて表示する。pointer/タッチの代替操作も記載し、キーだけを唯一の操作手段にしない。
- 検索入力・結果選択は日本語IMEを尊重する。compositionのEnterを記事選択として消費しない。

## 5. 画面と操作

### 5.1 ヘルプへの入口

Desktopはサイドバー下部の補助導線、MobileはMore等から「ヘルプ・アプリ情報」へ移る。検索語なしでもカテゴリから調べられる。ログイン画面からも基本の利用案内と問題解決を参照できる設計とする。

画面別の「使い方」、項目の説明ボタン、エラーの「解決方法」は対応する記事を直接開く。ヘルプを探すために毎回トップからカテゴリを選び直させない。

### 5.2 作業を保って読む

Desktopの文脈ヘルプは右側パネル、Mobileは記事画面またはsheetを使う案とする。ヘルプトップの全画面表示と、作業中に参照する案内を区別する。

- ヘルプの表示や記事間移動でアプリを再読み込みしない。入力中のPage、フォームの未確定値、スクロール位置を保つ。
- 閉じる/Backで起点の画面へ戻り、起点のcontrolへフォーカスを戻す。Editorから開いた場合は復帰時の選択位置も保つ。
- 本文を読むパネルとmodalなsheetは、それぞれ適切なkeyboard移動・閉じる操作を持つ。見出し、本文、リンクを読み上げやすい順にする。
- 必要な操作説明はkeyboard focusとタッチから読める。hoverだけの案内や色だけの状態説明にしない。
- 自動案内はフォーカスを奪わない。Editorのcomposition中に学習案内を開始しない。

### 5.3 初回案内と空状態

初回案内は最初の作業に必要な短い項目へ絞り、スキップ・閉じる・後で再表示ができる。完了やスキップの設定と再表示導線を用意し、起動のたびに同じ説明を強制しない。

練習が必要な場合は、練習用の一時データであることを示す。利用者のPage、Task、時間割へサンプルを自動追加しない。空状態は、その画面で最初にできる操作と対応する記事を示す。

## 6. Offline・版・記事管理

基本ガイド、FAQ、保存・同期・データ保全の問題解決手順、記事検索索引をアプリへ同梱する。接続できないときに必要な説明をネットワーク取得だけにしない。

Webでは記事をアプリ資産として保持する設計とし、offline初回起動等の対応範囲はWeb local store/配信方針と合わせて確定する。外部記事・問い合わせなど接続が必要な導線はその条件を示す。

- 記事は安定したarticle ID、タイトル、カテゴリ、用語別名、locale、対応platform、対象機能、記事の改訂版を持つ案とする。
- ヘルプ記事は利用者のPage/Y.DocやTaskと分けた製品コンテンツとする。アプリ版と同じリポジトリで変更をレビューする案とし、編集形式・配信方式は実装時に選ぶ。
- 内部リンク・エラーからの記事参照はarticle ID等の安定した識別子に対応させ、記事名の変更だけで導線を壊さない。
- 公開する機能の変更では対応記事とショートカットを見直す。未提供/無効な機能の手順を通常の検索結果や初回案内へ出さない。
- 版違いや利用できない記事へ移った場合は現在の版で利用可能な説明とヘルプトップへ案内し、空白画面や無効な操作ボタンで終わらせない。
- 翻訳と画像は本文の改訂に追従させる。画像だけに必要な手順を閉じ込めず、説明文と代替テキストを用意する。

## 7. 問題解決と診断

エラー記事は利用者が画面上で確認できる状態を起点とし、確認、実行できる操作、結果の確認という順序で説明する。

| 状態 | 案内の方向 |
| --- | --- |
| offline / 接続失敗 | 端末保存状態と接続状態を確認し、利用できる作業と再接続/再試行を案内 |
| ローカル保存エラー | 状態を明示し、内容を保全する手順と診断へ誘導。「保存済み」と言い切らない |
| 同期Conflict | 解決画面で候補を比較し、選んだ値を確認する手順 |
| 権限エラー | 対象workspace/resourceへの権限確認へ誘導。再試行し続ける手順にしない |
| 予定が見えない | 日付範囲、表示フィルタ、グループ/期間、取消/振替先を確認する手順 |
| アプリ更新ができない／更新後に起動しない | `APP_UPDATE_SPEC.md`に沿って更新段階・実行版・端末保存を確認し、未送信データを保全して再試行/復旧を案内 |

一般的な解決手順を、DB消去・アプリ初期化・pending操作削除から始めない。データ保全と現在の状態を踏まえた復旧方針にする。記事を読むだけでは設定変更・再試行・データ変更を自動実行しない。

診断の最小情報はアプリ版、platform、現在の保存/同期状態、エラー種別等とする。token、認証情報、Page本文、Yjs binary、Task/予定の内容を標準の診断情報へ含めない。詳細ログの範囲とredaction契約は運用仕様で確定する。

利用者が内容をプレビューし、コピーまたはファイルとして書き出す。問い合わせ送信は送信先・範囲を示して利用者が選ぶ独立した操作とし、自動アップロードを前提にしない。具体的な問い合わせ先・対応体制・送信機能が未決定の間は、機能するように見える送信ボタンを作らない。

## 8. 受入条件の案

| ID | 操作・条件 | 期待結果 |
| --- | --- | --- |
| HELP-01 | Desktop/Mobileからヘルプを開き、検索せずに利用方法を探す | keyboard/タッチで入口・カテゴリ・記事へ到達できる |
| HELP-02 | Editor/フォームの入力中に文脈ヘルプを開き、関連記事を読み、戻る | 入力、作業位置、復帰フォーカスが保持される |
| HELP-03 | 「休講」「中止」「補講」「追加開催」で検索する | 休講/中止は取消、補講/追加開催は追加の説明へ到達でき、振替と追加の違いも分かる |
| HELP-04 | 合致しない語句を検索し、カテゴリへ切り替える | 検索語を失わず、再検索とカテゴリ閲覧ができる |
| HELP-05 | 取得済みのアプリでoffline/未ログインの状態から基本ガイド・FAQ・同期の問題解決を開く | 同梱の説明を読める。接続が必要な外部導線を区別する |
| HELP-06 | 対象platform/版で未提供の機能の記事へ移る | 未対応を分かる形で示し、利用可能な案内へ戻れる |
| HELP-07 | 初回案内をスキップして後で再表示する | 通常の作業を開始でき、実データを変更せず再学習できる |
| HELP-08 | 同期/保存/権限エラーから解決方法を開く | エラーに合う記事へ直接移り、保存状態を偽装せず確認・保全・対処できる |
| HELP-09 | 診断情報をプレビューしてコピー/書き出す | 秘密情報・本文を含まず、確認した範囲だけを扱い、自動送信しない |
| HELP-10 | 日本語IME、keyboard、読み上げ、タッチで検索・記事閲覧を行う | compositionを消費せず、hoverや画像だけに依存せず操作できる |
| HELP-11 | 機能名/手順/shortcutを変更して公開する | 記事・文脈リンクも更新され、リンク切れと提供状態の矛盾を検出できる |

これらは将来の製品実装に対する条件であり、現在のPoCの試験結果には含めない。

## 9. 次に確定する項目

- 初期記事、最初の案内の範囲、初期リリースへの提供時期。
- 記事の編集形式、配信・cache・更新契約、locale/翻訳の運用。
- 画面/操作/error IDと記事の対応、ヘルプへのshortcut割当。
- 問い合わせ先、対応体制、診断情報の追加範囲・保持方針。

Calendar・Editor等の実装計画へ対応する記事と文脈リンクを含め、公開時の検証項目として扱う。
