# アプリ内更新 設計案 v0.1

更新: 2026-10-01。ユーザー指定と回答に基づく製品設計。更新の検知、利用者が開始するダウンロード、確認後のインストールを追加する。未実装であり、PoCの範囲・実装順序・Gateは変更しない。

## 1. 決定事項と適用範囲

- 起動時と定期的に更新を検知する。設定の「アプリについて／更新」から手動確認もできる。
- 更新を見つけても自動ダウンロードしない。利用者が開始する。
- ダウンロード後は「今すぐ更新／後で」を選び、アプリを終了・再起動する前に確認する。次回終了時や指定時刻の自動インストールは初期仕様に含めない。
- 端末への保存完了を確認し、未送信データを保持してから更新する。同期完了は更新の必須条件にしない。

初期の設計対象はWindows desktopのTauriアプリ。macOS/Linuxは対応する配布形式ごとに検証して追加する。Android/iOSのストア配布はストアの更新導線、Webは配信済みfrontendの再読み込み導線として別契約にする。desktop用インストーラを共用しない。提供時期は実装計画で確定する。

## 2. 更新の検知と案内

起動後、ローカルデータの復元と通常画面の表示を優先し、更新確認はバックグラウンドで行う。定期確認はアプリ起動中のみ行い、休止復帰や再接続で同時確認を増やさない。確認間隔・timeout・再試行上限は実装前に確定する。アプリが終了している間の常駐サービスは導入しない。

設定画面には実行中の版、公開されている版、最終確認時刻、更新内容、状態と次の操作を表示する。比較には実行物の版を使う。リポジトリの`VERSION`やGitタグが増えたことだけで更新ありにしない。

新しい版の案内は作業を遮らない通知または設定の印で示す。同じ版を「後で」にしたら、定期確認のたびに通知を繰り返さない。設定から再び開ける。IME composition中はfocusを奪うDialogを自動表示しない。

| 状態 | 表示・操作 |
| --- | --- |
| 確認前／確認中 | 最終成功確認時刻と「確認中」。編集を継続できる |
| 更新なし | 「この配布経路では最新です」と確認時刻 |
| 更新あり | 現在版→更新版、更新内容、対応環境、取得サイズが分かればサイズ、「ダウンロード」「後で」 |
| ダウンロード中 | 取得済み容量と進捗。総量不明なら不確定表示。編集を継続できる |
| ダウンロード完了・検証済み | 「今すぐ更新」「後で」。取得完了とインストール完了を区別 |
| 保存待ち | 「変更を端末に保存しています」。保存エラーなら更新へ進まない |
| インストール中 | 進捗と再起動の案内。installerへ引き継いだ状態を成功と断定しない |
| 確認／取得／検証／導入失敗 | 失敗段階、再試行またはヘルプへの導線。編集データを初期化しない |

通信失敗・offline・配信停止を「最新」と扱わない。確認失敗は保存や同期のエラーと分ける。更新通知はARIAで伝え、keyboardで操作・延期でき、閉じた後は元のfocusへ戻す。更新内容は非信頼入力としてtextまたは安全に制限したMarkdownで描画する。

## 3. ダウンロードとインストールの境界

Tauri updaterの`download()`と`install()`を分離し、ダウンロード開始の同意が終了・インストールの同意を兼ねないようにする。署名検証済みの対象だけをインストール候補にする。Windowsでは`install()`がinstaller起動後にアプリを終了するため、再起動確認・保存処理は呼び出し前に完了させる。[Tauri updater API](https://v2.tauri.app/reference/javascript/updater/)。

「今すぐ更新」を選ぶと「更新のためGreivaを終了します。端末に保存した変更と未送信データは保持します」を示す確認画面を開く。「更新して再起動／キャンセル」を設ける。IME変換中の入力を強制確定せず、変換の確定または取消を待つ。

確認後は次の順で処理する。

1. 新規の入力・操作開始を一時停止し、複数windowを含めて実行中のデータ変更を完了させる。音声録音や処理中のAI操作などの中断方針は当該仕様と整合させ、勝手に破棄しない。
2. PageのCRDT update、metadata、Task/Relation/予定等の変更とpending operationを各保存契約に従ってcommitする。書込み中のSQLite WALをコピーするだけの保全は行わない。
3. 保存完了・復元可能性を確認する。保存失敗・未確定入力・中断できない操作がある場合は導入を中止し、アプリを開いたまま対処を案内する。
4. 対象版・署名・platform/architectureとschema/protocolの互換性を再確認する。必要な整合したbackupを作成してからinstallerへ引き継ぐ。
5. 更新後の起動で実行版、local DBの復元・migration結果を確認し、前回のPage/作業場所へ戻す。同期は保存済みのqueue/cursor・Yjs差分から再開する。

保存済みで未送信の変更は削除・ACK済み扱いにしない。serverへ接続できなくてもlocal保存と互換性の条件を満たせば更新できる。完了後は成功を非遮断の案内で伝える。OSが起動を阻止した場合やinstallerが失敗した場合も、次回起動時に残った更新記録を確認して正しい状態を示す。

## 4. 配布・署名・互換性

Tauri 2 updaterを第一候補とする。公式仕様ではupdate artifactの署名検証が必須であり、本番の更新endpointにはTLSを使う。公開鍵をアプリへ組み込み、秘密鍵はリポジトリ・配布物・ログへ含めずrelease環境で管理する。[Tauri updater guide](https://v2.tauri.app/plugin/updater/)。Windows installerのOS用code signingはupdater署名と別の公開前要件として整理する。

公開単位は「検証済みの実行物＋署名＋platformごとのURL＋版＋更新内容」。全対象のuploadと検証を完了してからmanifestを公開する。GitHub Releasesを配信元の候補とし、通常のcommit/tag pushだけでは更新を配信しない。既存の開発チェックポイント運用は[versioning.md](../development/versioning.md)を維持する。

初期提供では安定版の配布経路を基本とする。pre-releaseへの参加、公開停止、段階配信、鍵のrotation/recoveryはrelease運用で確定する。古いmanifest・同一版・旧版を取得しても自動downgradeしない。OS/architecture/配布形式が一致しないartifactを選ばない。

local DB schema・Y.Doc schema・同期protocolとアプリ版は独立管理する。古いクライアントが残る期間のserver互換性と、migrationが必要な版の更新経路を明示する。migration失敗時にDBを消去して再同期しない。不可逆migration後に実行物だけを旧版へ戻さず、互換性を保証した復旧・roll-forwardを用意する。

downloaderの一時領域はアプリの管理領域に置き、本文DBやpending queueと分離する。取得物の起動をURL・任意のshell commandへ直接委譲しない。容量不足、検証不一致、proxy/通信timeout、権限不足、installer中断を別の失敗として扱う。延期したダウンロードをプロセス再起動後も保持するか、取得中断・再開を提供するかは実装前に決める。plugin標準APIだけで永続cacheやresumeが実現済みとは扱わない。

## 5. 受入条件

| ID | 条件 | 期待結果 |
| --- | --- | --- |
| UPDATE-01 | 起動・定期・手動で確認する | 編集を妨げず、同時確認を抑制し、正しい実行版・時刻を表示 |
| UPDATE-02 | 新しい版を検知して延期する | 無断ダウンロード・終了がなく、同じ版の通知を繰り返さず後で開ける |
| UPDATE-03 | 利用者がダウンロードを開始する | 進捗を表示し、取得完了だけでは導入・終了しない |
| UPDATE-04 | 確認画面でキャンセルする | 編集とfocusが復帰し、installerを起動しない |
| UPDATE-05 | offline編集・pending operationを保持して更新する | 新版で本文・metadata・queueが復元され、再接続後に重複せず収束 |
| UPDATE-06 | 保存エラー・IME変換中・処理中に更新を選ぶ | データを破棄せず、条件が整うまで導入・終了をしない |
| UPDATE-07 | 通信断、容量不足、不正署名、platform不一致を注入する | 失敗段階を表示し、不正artifactを起動せず、元データを保持 |
| UPDATE-08 | installer・migration・初回起動を中断または失敗させる | 成功を偽装せず、整合したbackupと互換性のある復旧経路を保持 |
| UPDATE-09 | 同一版・旧版・pre-release・非公開checkpointを確認する | 公開した配布経路の適切な更新だけを提示 |
| UPDATE-10 | keyboard・読み上げ・日本語IMEで案内を操作する | focus移動・復帰と状態通知が機能し、compositionを強制確定しない |
| UPDATE-11 | サーバーと複数世代のアプリを組み合わせる | 許可する互換性範囲でpending再送・Yjs復元が成立し、非互換を明示 |

Dockerで検知・配信manifest・エラー・保存境界を自動検証し、Windows実機で署名付きinstaller・終了/再起動・実際のMicrosoft IMEを検証する。現在のPoCの成功結果をupdaterの成功結果に流用しない。

## 6. 次に確定する項目

- 提供時期・対象OS、Windowsの配布形式とinstall scope、更新endpointの運用主体。
- 定期確認間隔・再試行、更新cacheの期限・容量上限、中断/再開の提供範囲。
- signing key管理・rotation/recovery、OS code signing、公開/撤回と段階配信。
- backupとmigrationの具体契約、複数window・録音・AI実行の停止境界、復旧先の導線。

ヘルプには「更新方法」「更新できない」「更新後に起動しない」「端末保存と未送信データの保全」を追加する。診断は実行版・platform・更新段階・エラー種別を基本とし、本文・token・署名秘密鍵を含めない。
