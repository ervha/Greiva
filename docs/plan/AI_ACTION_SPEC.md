# AI・文章/音声によるアプリ操作 設計案 v0.10

2026-10-07追記：[個人情報・暗号化仕様](ACCOUNT_PRIVACY_ENCRYPTION_SPEC.md)により、本文のserver復号は許容するが、AI等への本文送信は利用者が明示した範囲だけに限定する。本文保護の緩和を全workspaceの自動送信や同意の省略へ拡大しない。以下の送信範囲・保持・録音選択を維持し、実データの外部送信を今回開始しない。

更新: 2026-10-01。ユーザー指定の将来機能を記録する。文章や音声入力からPage作成、Task・予定登録を行い、Greivaが提供する各操作へ段階的に対応できるようにする。以下の内部構成、操作例、受入条件は設計案であり、AI実装済みやアプリ初期リリースへの採用を意味しない。

## 1. 合意した方向と境界

- 文章入力と音声入力を、Greivaの実際の操作につながる入口として提供する。
- Page作成、Task登録、予定登録を具体的な利用対象とする。
- 将来追加する機能にも対応を広げられる、アプリに組み込まれた操作基盤として設計する。
- 実行前の確認は回答Bで決定: 新規作成は直接実行し、既存データの変更・削除は確認してから実行する（2026-09-30）。曖昧な情報への質問や権限・入力検証は省略しない。
- 参照範囲は回答Bで決定: 入力内容に加え、現在のPage・予定と、それに関連するノートやTaskを参照できる（同日）。
- 外部送信は回答Bで決定: 初回設定で送信先とデータの種類を許可し、その範囲内では毎回の送信確認を省略する。利用者は後から変更・解除できる（同日）。
- 音声の利用範囲は回答Bで決定: 短い操作指示に加え、会議・講義等の長い録音からPageを作成し、Task・予定の候補も抽出する（同日）。
- 録音からの候補登録は回答Aで決定: 候補一覧から登録したいTask・予定を選び、一括登録する。短い直接指示の新規作成は直接実行を維持する（同日）。
- 録音から作るPageの構成は回答Bで決定: 要点を整理したノートと、折りたたんだ全文の文字起こしを同じPageへ置く（同日）。
- 元録音の保持は回答Bで決定: アプリ側の初期設定は30日間保存で、期間を変更できる。録音の期限が来ても、作成したPageと文字起こしは保持する（同日）。
- 元録音の保存場所は回答Cで決定: 基本は録音した端末内へ保存し、必要な録音だけ利用者が選んでアプリのクラウドへ保存できる。AI Providerへの送信とは別の選択とする（同日）。
- 2026-10-01の一括回答1A: AIの初期提供は作成・登録・録音整理から始め、既存データの編集・削除や検索は順次追加する。
- 同回答2C: AIの入口は共通パネルと各画面の文脈に応じた入口を併用する。
- 同回答3A: アプリ内録音と既存音声ファイルの取込みの両方に対応する。
- 同回答4B: AI会話履歴は初期30日保存とし、期間変更と手動削除を可能にする。

ここでいうnative対応は、アプリのデータ・操作・保存・同期・権限と連動することを指す設計案である。端末内のAIモデル、特定のAI/音声サービス、OS全体の操作を採用する決定ではない。

`GREIVA_REQUIREMENTS.md`のapplication/domain分離、Page本文のCRDT正本、structured sync、認可とConflict保持を引き継ぐ。PoCの範囲と検証順序は変更しない。

### 1.1 AI初期提供の範囲（合意済み）

将来のAI機能の最初の提供範囲は、文章・短い音声指示によるPage作成、Task・予定の新規登録、録音/取り込んだ音声の整理とPage作成・候補抽出/選択登録とする。公開日は未決定であり、アプリの初期リリースへ同時に含める決定ではない。

既存データの編集・削除、利用者がAIへ依頼する検索・移動等は後続段階で追加する。作成・登録に必要な現在の対象と関連データの読み取りは5.1に従い、初期段階でも利用する。初期範囲外の依頼は通常画面の操作を案内し、対応済みのように実行しない。既存変更の確認規則は将来の拡張時にも適用する。新規作成に見えて既存データを変更する操作も、初期範囲へ紛れ込ませない。

## 2. 入力と利用例

| 入力の例 | アプリ内の候補操作 | 解決すべき情報 |
| --- | --- | --- |
| 「この内容で打合せノートを作って」＋文章 | Pageのタイトル・本文を作成 | 保存先workspace、内容、対象Pageの新規/既存 |
| 「明日までに資料を確認するタスクを追加」 | Task作成 | 基準日、期日、対象workspace |
| 「来週火曜15時から1時間、定例会を登録」 | 単発予定作成 | 具体的な日付、開始/終了、timezone |
| 「毎週月曜1限に演習。11月9日は休講」 | 定期予定と取消の操作案 | 適用期間、時限の設定、元の回 |
| 「この会議からノートと準備タスクを作って」 | 複数の操作案 | 対象予定、Page/Taskとの関連、実行順序 |
| 「この会議の録音をページにして、やることと次回の予定を拾って」 | 長い録音からPage作成とTask/予定候補の抽出 | 保存先、認識内容、日付の基準、候補の登録方法 |

これらは例であり、一度にすべてを公開する決定ではない。会議・習い事・個人予定等にも共通の操作を使い、大学用途だけに限定しない。

## 3. 共通の操作基盤の設計案

```text
文章入力 / 音声入力
  -> 音声の文字起こし・入力の確定
  -> 意図の解釈・必要な対象の参照
  -> 型付きの操作案
  -> 必須値・対象・権限・現在の状態を検証
  -> 確認ポリシーに従って実行
  -> 通常のapplication command
  -> local保存 / sync enqueue / CRDT変更
  -> 実際の結果を表示
```

通常UI、ショートカット、AIが共通のapplication commandを利用する案とする。AI専用の保存・同期・競合解決経路を増やさず、AIの出力は実行前に検証する操作案として扱う。

- commandは安定した識別子、型付き入力、対象・変更範囲、必要権限、実行結果、失敗理由、復元可能性を定義する案とする。
- 操作定義から、提供中の機能・platform・利用者の権限に適合したAI向けの操作一覧を構成する。未実装の操作を実行できると案内しない。
- AI/音声Providerはadapterの背後に置く。Provider変更がPage/Task/予定の保存形式を変える構成にしない。特定SDK・モデルは未選定。
- AIへDB/SQL、任意コード、OS操作の自由な実行権限を渡す構成にはしない。アプリが公開する検証可能な操作を通す案とする。
- 新しい機能を追加する際は、共通command、AIでの対応範囲、必要情報、確認/復元、ヘルプと評価例を一緒に定義する。全操作が無条件で同じ公開時期になるわけではない。

## 4. 解釈・確認・実行結果

音声は録音開始/停止と文字起こしの状態を表示し、訂正できる文章として扱う案とする。未確定の文字起こしで繰り返し登録を実行しない。マイク権限がない場合は文章入力を使えるようにする。

- 「明日」「来週」等は基準日時・locale・timezoneから具体的な値へ解釈し、その値を表示する。同名の対象や不明な時限、終了時刻等は必要に応じて質問し、勝手に埋めた値で確定しない。
- 新規/変更/削除、対象workspace/resource、変更前後、件数、関連付けを操作案として扱う。新規作成は直接実行し、既存データの変更・削除には確認画面を挟む。詳細は4.1の決定に従う。
- Calendarの既存予定の変更範囲は合意済みの「この回だけ／この回以降／全体」を使い、休講・振替の引き継ぎも通常UIと同じ確認・解決を通す。
- 読み取ったPage本文等は参照データとして扱う。本文中の指示によって利用者の依頼・権限・確認ポリシーを上書きしない。参照範囲は5.1、外部送信は5.2の決定に従う。
- 操作案を作った後に対象が変更された場合は再検証し、必要な再確認または既存Conflict処理へ進む。古い値で無断上書きしない。

Page本文の変更はEditor/CRDTのapplication経路、Task・予定・Relationはlocal transactionとsync enqueueの経路を使う。複数の操作がこれらをまたぐとき、全操作を単一DB transactionで確定できるとは約束しない。実行順序と操作ごとの結果、途中失敗時の継続/復元を設計する。

実行依頼と各操作の識別を保持し、同じ実行のretryでPage・Task・予定を二重作成しない案とする。利用者が意図的に新しく依頼した操作とは区別する。CRDT編集の重複防止と再開の詳細契約は実装前に定義する。

結果は「案を作成」「端末に保存」「同期待ち」「同期済み」「一部失敗」等を実際の状態に合わせて示す。生成結果を操作成功や同期済みの根拠にしない。作成した対象への導線を用意し、変更/削除の復元はアプリの履歴・Undo・Trashの契約に従う。

### 4.1 新規作成と既存変更の確認（合意済み）

| 操作 | 実行前の扱い | 実行後の案内 |
| --- | --- | --- |
| 新しいPage、Task、単発/定期予定を作成 | 入力・対象・権限が解決できれば、追加の確認クリックを求めず直接実行 | 作成した内容、具体的な日時・保存先、保存/同期状態と対象への導線 |
| 既存Pageの本文・属性、Task、予定等を変更 | 対象・変更前後・適用範囲・影響を示し、利用者の確認後に実行 | 変更結果と保存/同期状態 |
| 既存データを削除 | 対象・件数・影響を示し、利用者の確認後に実行 | 削除結果と通常のTrash/復元の導線 |

直接実行は、利用者が作成を依頼した確定入力に対する動作である。入力途中や音声の未確定認識、AIが独自に思い付いた操作の自動実行には広げない。必要な保存先、日時や時限、対象が分からない場合は質問してから作成する。既存データがある場合に、新規作成を無断で上書きへ変えない。

長い録音から抽出したTask・予定は4.3の一覧選択を使う。選択して「登録」を実行する操作が新規作成の依頼となり、解決済みの新規作成に別の確認クリックを追加しない。

新規作成と既存変更/削除を含む複合依頼では、各操作の区分と確認対象を示す。commandの名前が作成であっても、既存データを変更する効果を含むなら、その変更は確認対象とする。複合依頼の実行単位・順序・確認のまとめ方は後続設計で決める。

確認画面は修正・中止ができ、中止した既存変更/削除は実行しない。新規作成後の取り消し・訂正は通常の編集・Undo/Trashの契約に合わせて詰める。操作別に確認を省略する設定は今回採用した方針に含めない。

### 4.2 短い指示と長い録音の利用（範囲は合意済み）

音声は短い指示だけに限定せず、利用者が開始した会議・講義等の録音からPage作成、Task・予定候補の抽出にも対応する。音声入力元はアプリ内録音と既存音声ファイルの取込みとする。提供範囲は1.1に従い、最大録音時間・処理方式は未決定である。

| 使い方 | 目的 | 操作への接続 |
| --- | --- | --- |
| 短い操作指示 | 「明日までに資料確認を追加」等 | 確定した入力を通常のAI commandへ渡し、4.1の確認方針で実行 |
| 長い録音の記録・整理 | 会議ノート、講義ノート等をPageにする | Page作成の依頼に基づき、認識結果から内容を整理して作成 |
| 長い録音から候補を抽出 | やること、期日、次回の予定等を拾う | Task/予定の候補一覧から利用者が選び、一括登録 |

具体的な画面と処理は以下の案を検討する。

- 録音中、文字起こし中、整理/抽出中、Page作成済み、部分失敗を区別する。処理中も別のPageを編集でき、戻って処理状況と結果を確認できるようにする。
- 認識結果を確認・訂正できるようにし、整理した文章と元の認識内容を区別する。AIが推測した内容を実際の発言として記録しない。Pageは4.4の構成を使い、元録音の保持は5.3に従う。
- 抽出候補に、Task/予定の種別、名称、判明した日時・期日、元の発言箇所を示す案とする。発言箇所の時刻・文字範囲等の識別方式は後続設計で定義する。
- 「明日」「来週」等は録音の日時とtimezoneを踏まえて基準を示す。録音日時を特定できない場合や情報不足は質問し、処理した日を録音日と勝手に同一視しない。
- 録音中の会話は記録・参照データであり、発言を一つずつアプリ操作の依頼として実行しない。候補抽出だけの依頼は登録実行と区別し、4.3の一覧選択で登録する。
- 録音からPageを作る場合も、現在の対象・関連データの参照は5.1、外部への録音/文字起こし送信は5.2に従う。既存Pageへの追記・置換は4.1の確認対象とする。
- 同じ処理の再開・retryでPageや登録済みの候補を二重作成しない。録音・認識結果・抽出結果・作成先の対応と、部分失敗後に未処理部分だけ再開する契約を設計する。

- ファイル取込みは利用者が選んだ音声をアプリ管理下へコピーする設計とし、元のファイルを移動・削除しない。保持期限による削除もアプリ管理下のコピーだけを対象とする。取込みだけではマイク権限を求めない。
- 取り込んだ音声にも、文字起こしの訂正、整理したノートと全文、候補選択、保持期間と端末内を基本にした保存方針を適用する。ファイル選択だけでクラウド保存を開始せず、Provider送信も5.2の許可範囲を守る。
- 取込み日時を録音日時と同一視しない。録音日時を特定できない場合、相対日付の基準を利用者に確認する。

対応形式、長さ/容量/費用上限、ファイル選択とコピーのplatform差、録音の一時停止・background動作、話者表示、保存形式・削除処理の詳細は未決定。保持期間は5.3、保存先の利用方針は5.4で決定済み。

### 4.3 抽出候補の選択・一括登録（合意済み）

長い録音から抽出したTask・予定は候補一覧へ表示し、登録したいものを利用者が選んで一括登録する。内容が明確な候補でも、選択・登録の操作なしに自動登録しない。

- 一覧でTask/予定の種別、名称、判明した期日/日時、保存先、元の発言箇所を確認し、必要に応じて訂正できる案とする。選択しない候補は登録しない。
- 登録に必要な情報が不足している候補は、質問・編集で解決してから登録する。Taskの任意の期日と予定の必須日時を区別し、録音にない期日を勝手に補わない。
- 「選んだものを登録」を新規作成の依頼として扱い、4.1の直接実行方針へつなぐ。既存データの更新/削除を含む操作に変える場合は、4.1の確認を行う。
- 各候補に未登録・登録中・登録済み・失敗等の実状態と、登録した対象への導線を示す案とする。未選択・未登録の候補は通常のTask一覧やCalendarの確定予定へ混在させない。
- 一括登録は操作ごとの結果を保持する。途中失敗後のretryは未完了分を対象とし、登録済みの候補を同じ操作で二重作成しない。

選択の初期状態、全選択/解除の配置、重複候補のまとめ方、不足候補が混じる場合の一括登録の単位、候補の保持期間は後続UI/データ設計で定義する。

### 4.4 整理したノートと全文文字起こし（構成は合意済み）

録音から作るPageは、要点を整理したノートを主な本文とし、全文の文字起こしを同じPageの折りたたみ領域へ置く。最初は文字起こしを閉じて、必要なときに開けるようにする。

```text
録音から作成したPage
├─ 要点を整理したノート
│  └─ 要点・決定事項等（内容に応じた見出しは後続設計）
└─ 全文の文字起こし（初期状態は折りたたみ）
   └─ 元の認識内容を確認・訂正する入口
```

- 整理した文章と全文の文字起こしは見出し・ラベルで区別する。要約や推測を発言の逐語記録として表示しない。
- 長い全文でも、折りたたみの開閉、読む位置への移動、選択・コピー・訂正をkeyboard/タッチで扱えるようにする。開閉で文字起こしを削除しない。
- 抽出候補の根拠となる発言箇所から、対応する文字起こしへ移れる導線を設計する。折りたたみを必要に応じて開き、対象箇所を示す案とする。候補の登録方針は4.3を維持する。
- Page作成後の本文・文字起こしの訂正、再整理による置換は既存Pageの変更であり、AI操作は4.1の確認を通す。利用者が編集したノートを再処理で黙って上書きしない。

全文文字起こしを残すことと元録音の保持は分ける。音声は5.3の期間と5.4の保存方針で保持し、期限後もPageと全文を参照できる。保存方式の詳細、認識結果の改訂と候補の根拠参照の追従、話者/時刻ラベル、ノートの見出しテンプレートと大きな全文の表示方式は後続設計で決める。

### 4.5 共通パネルと各画面の入口（合意済み）

アプリ全体で利用できる共通AIパネルと、Page・Task・Calendar・録音等の画面からその文脈で使う入口を併用する。同じ操作基盤と確認・参照・送信方針を使い、入口ごとに実行規則を変えない。

- 画面から開く場合は、起点となる対象を明示する。共通パネルでも使用する対象を確認でき、別画面への移動で処理中の対象を黙って切り替えない。
- 入口を切り替えても入力の下書きと進行中の処理・結果を引き継ぐ案とする。パネルを閉じることと処理の中止を区別する。復帰時に同じ登録を再実行しない。
- Editorの選択・下書き・IME変換を保ち、パネルを閉じた際に元の操作へ戻れる設計とする。提供中の機能と権限に応じて利用可能な操作を示す。

具体的な配置、ショートカット、mobileでの表示形式、初回案内、処理中の閉じ方は後続UI設計で定義する。

## 5. AI設定・データ利用・利用可能な範囲

- AIを使わない通常操作も利用できる。クラウドAIがofflineで使えなくても、通常の閲覧・編集・保存の経路を妨げない。
- 端末内/クラウドの推論・音声認識、サービス、認証・費用・利用上限は未決定。offline AI対応を実装済みとして案内しない。
- 参照範囲は5.1のとおり、現在のPage・予定と関連するノート/Taskまでとする。参照できることと外部へ送信できることは別の条件として扱い、5.2で許可した範囲だけを送信する。
- 読み書きは通常の認可を通す。AI応答や候補に権限外のresourceを含めない。
- アプリ側の元録音の保持期間は5.3、AI会話履歴は5.5に従う。操作の実行記録やProviderでの利用条件は別のprivacy/運用契約で確定する。Page内の文字起こしはPageの保存・削除の契約に従う。内容とtokenを標準診断ログへ出さない。
- 音声認識誤り、処理中、取消、接続失敗、実行失敗を区別する。入力の保全、再試行、途中まで実行した結果の確認ができる案とする。

### 5.1 現在の対象と関連データの参照（合意済み）

利用者の入力文章/確定した音声入力に加えて、現在のPage・予定と、それに関連するノートやTaskを必要に応じて参照できる。毎回すべてを手動で選び直す運用には限定しない。

- 現在の対象を起点に、アプリ内のRelation等で関連する内容を解釈に使う。workspace内の無関係なデータを自動で横断検索する方針は今回採用していない。
- AIの入力時点で現在の対象を識別し、参照した対象を利用者が確認できる一覧等を用意する案とする。画面移動で別の対象へ黙って切り替えない。対象がない場合や特定できない場合は、入力だけで処理できるかを判断し、必要なら質問する。
- 関連先を含めて読み取り権限を検証する。権限外のデータは本文・名前・候補として渡さず、関連付けがあるだけで認可を省略しない。
- 操作の目的に必要な内容を参照する。関連の判定、辿る深さ、件数/本文量の上限、除外する操作、履歴の扱いは後続設計で定義する。関連先を無制限に辿る実装をこの回答だけで確定しない。
- アプリ内で参照可能な情報でも、外部送信は5.2の設定を満たす必要がある。録音は文章・文字起こしとは別のデータ種別として扱い、workspace全体の外部索引化は今回の範囲に含めない。アプリ側の元録音は5.3に従い、外部Providerの保持・削除条件と選定は後続設計で決める。

### 5.2 初回設定による外部送信の許可（合意済み）

利用者が初回設定で送信先とデータの種類を確認して許可する。許可済みの送信先・種類と5.1の参照範囲内では、AIを使うたびに同じ送信確認を求めない。具体的なProviderと設定項目の表現は後続設計で選ぶ。

- 送信先、処理の目的、送信するデータ種別を設定で示す。入力文/文字起こし、現在のPage・予定、関連するノート/Task等を区別できる案とする。音声認識サービスへ送る録音は別種別として明示する。
- 送信を許可しない種類は送信対象から除外する。必要な情報を使えない場合は利用可能な入力・操作を案内し、許可済みの種類へ無断で置き換えて送らない。
- 許可済みの送信先・種類の範囲を広げる際は、追加する範囲を示して設定で許可を得る。別Providerへの自動切替も送信先の許可を検証する。
- 設定を後から確認・変更・解除できる。解除後の新規送信・再送は停止し、送信時点の許可を検証する。送信済みデータの保持・削除と、処理中の取消の詳細は後続の運用契約で定義する。
- 外部送信の許可と操作実行の確認は別の設定である。送信確認を省略しても、4.1で決めた既存データの変更・削除の確認を省略しない。

設定の保存単位（account/workspace/端末）、許可の版管理、設定同期、送信先の表示粒度と記録の保持期間は未決定。今回の回答は将来のアプリ利用者向けの設定方針であり、現在の開発でサービス接続や実データ送信を行う指示ではない。

### 5.3 元録音の保持期間（初期設定は合意済み）

アプリが管理する元録音は初期設定で30日間保持し、利用者が保存期間を変更できる。期限後は元録音を自動削除する設計とする。Page、全文の文字起こし、登録済みTask・予定はこの期限に連動して削除しない。

- 設定で現在の期間を確認・変更でき、録音ごとに保持期限と保存/削除状態を確認できる案とする。期間設定の保存単位、起算時点と変更後の既存録音への適用は後続設計で定義する。
- 元録音の期限が来ても、整理したノートと全文を読め、候補の根拠となる文字起こしを確認できる。音声がなくなった場合は再生・音声からの再認識が利用できない状態を示す。
- 削除の処理はアプリ管理下の音声ファイル・cache等の保存先に合わせて設計する。offline等で処理が完了していない場合は実際の状態を保持し、未削除の録音を削除済みと表示しない。再開後の削除と検証を運用契約へ落とす。
- AI Providerへの送信許可は5.2、Provider側の保持・削除条件は別の契約である。アプリ側の30日設定が、外部Providerの保存期間も30日になることを意味する表示にしない。

保存先は5.4の方針に従う。期限前の手動削除、容量制限、backup上の保持と削除、処理中/失敗した録音の期限到来時の扱いは未決定。今回の回答で無期限保存や特定のクラウドサービスは選定していない。

### 5.4 端末内保存と選択した録音のクラウド保存（合意済み）

元録音は基本的に録音した端末へ保存する。利用者が必要な録音を選んだ場合だけ、アプリのクラウドへ保存し、権限のある他の端末からも利用できる設計とする。全録音の自動アップロードを初期状態にしない。

- Pageと文字起こしは通常の保存・同期を使う。元音声をクラウドへ保存しなくても、同期したPageや文字起こしを他の端末で読める。
- 元音声は「この端末のみ」「クラウド保存待ち/保存中」「クラウド保存済み」「失敗」「期限切れ」等の実状態を確認できる案とする。未完了のアップロードを保存済みと表示しない。
- 端末だけにある音声を他端末で開いた場合は、その端末で利用できないことを示す。録音した端末に音声があることと、現在の端末で再生できることを区別する。
- クラウド保存は利用者が録音を選んで開始する操作とする。接続できない場合の待機・再送、途中失敗からの再開と重複防止を設計する。権限は通常のworkspace/resource認可と連動させる。
- アプリ側の端末・クラウド保存には5.3の保持方針を適用する。アップロードによって期限が黙って延長されない設計とし、期限・各保存先の削除状態を追跡する案とする。端末間の期限/削除同期とcache/backupの処理は後続設計で定義する。
- アプリのクラウド保管と外部AI/音声Providerへの処理用送信は別の操作である。クラウド保存を選ばなくても、5.2で許可したProviderへの処理用送信は可能であり、その送信によってアプリのクラウド保管が自動で有効になることはない。

クラウドサービス、object/録音IDの対応、保存形式、暗号化、容量・費用・通信上限、他端末でのcache、クラウド保存解除と期限前の削除操作は未決定。今回の決定は将来の保存方針であり、現在の録音や利用者データをアップロードする指示ではない。

### 5.5 AI会話履歴の保持（合意済み）

アプリが管理するAIの会話履歴は初期設定で30日保存し、利用者が保存期間を変更でき、期限前にも手動で削除できる。対象はAIとの入力・応答の会話であり、元録音の保持設定とは分けて表示・管理する。

- 履歴が期限切れまたは手動削除になっても、作成したPage・全文文字起こし・登録済みTask/予定を削除したり、操作を取り消したりしない。元録音は5.3の期限に従う。
- 保存された会話を開き直しても、以前の作成・登録を自動再実行しない。必要な操作のretry識別や同期・Conflict・監査の記録は会話本文と別に定義し、会話削除によって重複防止を失わない。
- アプリ側の履歴削除と外部Provider側の保持・削除を区別する。処理未完了の削除を完了済みと表示しない。

履歴の保存単位・保存先・端末間同期、期限の起算、変更後の既存履歴への適用、設定できる期間、進行中処理との関係、backupとProvider側の保持・削除契約は後続設計で確定する。
