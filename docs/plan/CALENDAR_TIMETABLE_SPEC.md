# Calendar・定期予定・時間割 設計案 v0.3

更新: 2026-10-01。製品要件の追加と、実装前に検討する詳細設計をまとめる。v0.3では汎用DB・Board・Buttonとの接続を追加した。機能要求と登録方法はユーザー指定に基づく。以下の具体的なモデル・画面・受入条件は設計案であり、実装済みや初期リリース確定を意味しない。

## 1. 合意した要求と位置付け

- Greiva内で時間割を登録し、Calendarビューに表示する。
- 時間割の登録は曜日＋時限を基本とし、時刻も自由に指定できる。
- 原則の曜日ごとの繰り返しと、休講・振替・補講等に対応する。
- 大学専用にせず、シフト、習い事、練習、定例会、個人の定期予定等にも使える汎用モデルとする。
- 定期予定の変更範囲は「この回だけ／この回以降／全体」の3択とする。「この回以降」では過去の予定を保持する（2026-09-30の回答で決定）。
- まとめて変更する際は、休講・振替の引き継ぎ案を自動で用意し、一覧で確認・修正してから確定する。対応する回へ休講を引き継ぎ、振替先の日時は保持する。対応を判断できない例外は個別に確認する（同日の回答Aで決定）。

本書は`GREIVA_REQUIREMENTS.md`・`GREIVA_DESIGN_SPEC.md`の追加詳細である。local-first、structured sync、Conflict保持、Provider Adapterの境界を引き継ぐ。`POC_SPEC.md`の実装範囲とSection 18の順序は変更しない。Calendarのコード、DB migration、同期DTO、実画面は本変更に含めない。

## 2. 同じ機能を用途に合わせて使う

| 共通概念 | 大学等の時間割 | 他の用途の例 |
| --- | --- | --- |
| 予定名 | 授業名 | シフト名、習い事、練習、定例会 |
| 任意のグループ/期間 | 2026年度後期・学期 | 勤務パターン、チーム活動、期間指定なし |
| 時間帯プリセット | 1限・2限 | 早番・遅番、午前・夕方、利用しない |
| 原則の繰り返し | 毎週月曜1限 | 毎週火木18:00、隔週金曜の定例会 |
| 一回の取消 | 休講 | 中止、休み |
| 一回の日時変更 | 振替授業・教室変更 | 日程変更、勤務地変更 |
| 追加の開催 | 補講 | 臨時シフト、追加レッスン、臨時会合 |

「授業」専用テーブルを汎用カレンダーの中核にしない。大学向け名称・入力補助を共通モデルに重ねる。学期、時限、教室、担当教員は汎用予定の必須項目にしない。

## 3. 登録と繰り返しの設計案

### 3.1 基本の登録

定期予定の最小入力は予定名、開始日、曜日、時限/時間帯または開始・終了時刻。単発予定は日付と時刻を指定し、繰り返す曜日は求めない。時間割利用時は学期を選ぶことで期間と時限設定を入力補助できる。場所・担当者・色・説明は任意とする。

- 時間帯プリセットは名称と開始・終了時刻を利用者が設定する。90分授業、固定の1限開始時刻、平日だけを前提にしない。
- 同じ予定に複数の曜日・時間帯を登録できる。曜日ごとに時間や場所が違う場合も別の繰り返しパターンとして扱う。
- 開始日と任意の終了日で適用期間を定義する。学期を使う場合は学期の範囲を反映する。終了日のない定期予定も扱える。
- 時限を使わない予定は時刻を直接指定する。日をまたぐ場合は終了が翌日以降であることを明示し、単に終了時刻が開始時刻より小さい値として保存しない。
- プリセットから取り込んだ実時刻や学期から取り込んだ適用期間は、予定の定義に保持する。プリセット/グループ設定を変更しても登録済み予定の時刻・期間を黙って変更しない。既存予定への一括適用は対象と変更結果を確認する別操作とする。

### 3.2 原則の繰り返し

初期設計の中心は、全曜日を選択できる週単位の繰り返しとする。毎週は間隔1、隔週は間隔2として扱い、週の起点を保持する。「第何週か」を表示月や端末設定から推測しない。

- 各パターンは曜日集合、週の間隔、基準週、適用期間、時間帯、予定のタイムゾーンを持つ。
- 基準週は予定のタイムゾーンで月曜開始の週境界として保持する案とする。画面の週開始曜日とは独立させ、表示設定を変更しても繰り返し結果は変えない。
- 原則の回は開始日・終了日の双方を含む期間に生成する。終了日なしでも、表示範囲＋必要な小さな余白だけを展開し、全将来分をDBへ作らない。
- 祝日を一律に休講/取消にしない。利用者が設定した休止日・休止期間を適用する。祝日カレンダーや学校・組織の暦の自動取込みは別の判断とする。
- 月単位、年単位、勤務ローテーション、複雑な繰り返しは拡張候補とする。週単位の規則の中へ特殊条件を詰め込まず、規則種別を追加可能な境界を設ける。

## 4. 取消・振替・追加

| 操作 | 保存する意味 | Calendar表示・他の回への影響 |
| --- | --- | --- |
| この回を取消 | 元の回を指定した取消例外 | 「取消」/「休講」を明示。他の回の規則は維持 |
| この回の日時・場所を変更 | 元の回を指定した上書き例外 | 振替先に有効な予定を1件表示。元の日時を詳細に残す |
| 回を追加 | 独立IDを持つ単発予定。元の定期予定へ任意で関連付け | 「追加」/「補講」を表示。原則の回を移動・削除しない |
| 繰り返しの設定を変更 | 対象期間を明示した規則変更 | 一回の例外と区別し、影響する回・既存例外を確認 |

振替と補講は混同しない。振替は既存の一回の移動、補講は追加開催である。取消した回の補講を追加する場合は、その回への関連を保持できるが、元の回が勝手に復活することはない。

- 例外は「元のパターンID＋元の開催日」を参照する。表示日を変更してもその元の回の識別子を変えない。
- 追加予定は独立IDを使う。同日の同じ定期予定に複数回追加でき、再送では同じIDが重複作成されない。
- 取消/変更の例外は、一つの元の回について一つの有効状態として解決する。複数端末から異なる変更が届いた場合はConflictとして保持する。
- 個別の例外を、グループ全体の休止日/期間より優先できる。休止日でも明示的な振替や追加開催を登録できる。
- 学期等の終了後に振替・補講を行う場合も、確認のうえ単発の例外/追加として登録できる。学期全体の繰り返し期間は自動延長しない。
- 規則の曜日や期間を変更して元の回がなくなる場合、関連する例外を黙って破棄しない。再適用、単発予定として保持、取り消し等の扱いを変更前に示す。詳細な履歴・期間分割モデルは`DATA_MODEL.md`で確定する。
- 例外の解除で原則の予定へ戻せる。予定削除と一回の取消は別操作にし、削除には復元導線を持つ。

### 4.1 変更範囲の選択（合意済み）

| 選択 | 変更する範囲 | 保持する内容 |
| --- | --- | --- |
| この回だけ | 選択した一回の日時・場所等 | 原則の繰り返しと他の回 |
| この回以降 | 選択した回を起点とする、その後の繰り返し | 起点より前の予定と、その回の取消・振替等の状態 |
| 全体 | 対象の定期予定全体 | 既存例外への影響を確認してから確定。過去を含む影響範囲も明示 |

「この回以降」で過去の曜日・時刻を新しい設定へ書き換えない。利用者が旧予定を終了して新しい予定を手動で登録し直す必要はない。

確定前に適用範囲と既存の休講・振替への影響を表示する。引き継ぎの操作方針は4.2のとおり決定済み。複数パターンの対象範囲、振替済みの回の境界日判定、全体変更時の履歴表現と内部の期間分割・識別子の契約は後続の設計で定義する。

### 4.2 休講・振替の引き継ぎ（合意済み）

「この回以降」「全体」で原則の設定を変更する際は、引き継げる例外について維持する案を初期選択として用意する。利用者は一覧で確認・修正し、変更と引き継ぎを確定する。案の表示だけでは予定を書き換えない。

- 休講/取消は、新しい規則の対応する回へ引き継ぐ案とする。例えば11/09（月）の休講指定は、対応関係が明確な場合は11/10（火）の回を取消とする案を示す。
- 振替は元の回との対応を引き継ぎ、個別に決めた振替先の日時を保持する。原則の曜日・時刻変更だけでは、振替先を一緒に移動しない。
- 確認一覧では元の回、新しい対応先、取消/振替の種別、振替先の日時、引き継ぎ案を示す。各例外は案を維持するか、解除して新しい原則へ戻すかを選べる。
- 対応する回がなくなる場合や、複数の候補があって判断できない場合は「要確認」として個別に扱う。黙って破棄・任意の回へ割り当てず、扱いを選んでから確定する。保持・再割当等の詳細選択肢は後続の画面/データ設計で詰める。
- 「この回以降」より前の例外は変更しない。独立した補講/追加開催はこの引き継ぎ処理で移動・削除しない。

対応関係の判定規則、期間分割後の元の回の識別、競合時の再確認は未決定であり、実装前にデータモデルと同期仕様へ落とす。

## 5. Calendar UIの設計案

### 5.1 週表示を共通の確認導線にする

Calendarの通常予定と時間割・定期予定を同じ日時の軸で表示する。別々の画面に置いて予定の重複が分からなくなる構成を避ける。

```text
Calendar  [今日] [前週] [次週]   [月 / 週 / 日 / 一覧]   [+予定]
表示対象  [通常予定] [定期予定・時間割]   グループ [すべて ▼]

時刻・時間帯     月         火         水         木         金 … 土・日
09:00  1限      情報科学              情報科学
10:40  2限                 演習                            演習
18:00           定例会                練習        追加練習
```

これは情報構造のwireframeであり、色・寸法・Calendarライブラリの確定ではない。

- 週表示では実時刻に比例した位置へ配置し、設定された時限/時間帯ラベルを補助として併記する。時限の間の休憩や時刻指定の予定を隠さない。
- 月表示は予定名・短い日時表示、日/一覧表示は日時・場所・例外を読み取りやすくする。狭い画面では一覧を使え、週の横スクロールだけに依存しない。
- 同じ画面でグループや表示対象を切り替える。非表示の予定は削除されない。終了した学期/期間の時間割も過去の日付で確認できる。
- 同時刻の予定は並列に表示し、重なりを隠さない。「予定の重複」は同期Conflictとは別の注意として扱う。保存は禁止せず、取消済みの回は有効な予定の重複に数えない。
- 一回の取消は淡い表示＋明確な文言、振替/変更と追加はbadge等で識別する。色だけに依存しない。
- 振替の元の日時は詳細から確認できる。有効な同じ回を元の日時と振替先に二重表示しない。

### 5.2 登録と詳細操作

Calendarの「追加」から単発予定または定期予定を選び、時間割利用時は時限設定を使う。グループ/期間と時間帯設定へはCalendar内から到達できる。大学利用だけの上位ナビゲーションは増やさない。

各回の詳細では、原則の設定、今回の日時、取消/変更/追加の種別を区別する。「この回を取消」「日時を変更」「回を追加」「繰り返しの設定」を別の操作として示す。定期予定の変更では「この回だけ／この回以降／全体」を選べるようにし、適用期間と影響する既存の回・例外を確認する。

Dragによる移動は一回の日時変更として扱う。全体の曜日や時間帯を勝手に変更しない。Dragを使わなくてもフォームとkeyboard/タッチで同じ変更ができる。

Desktopの詳細パネルとMobileのbottom sheetは同じ変更範囲・検証を使う。閉じた後は選択した予定へフォーカスを戻す。読み上げ名は予定名・日付・時刻・取消等の状態を含める。

### 5.3 汎用DBビュー・カード・ボタンとの接続

時間割は[DATABASE_SPEC.md](DATABASE_SPEC.md)の汎用Boardを、Group=曜日・Subgroup=時限・Filter=期間等で設定する利用例とする。列/行、カードの区分・場所・期間表示、関連Task/Pageを作るButtonは任意のPropertyとactionで設定でき、科目専用schemaや固定の「課題追加」「講義ノート追加」を中核へ実装しない。同じ仕組みを担当者×勤務帯、状態×優先度等に使える。

RecordとSchedule bindingを通して同じ正本を参照し、原則を示すBoardと各回の実日時を示すCalendarを区別する。複数曜日と複数時限の直積から開催規則を推測せず、RecurrencePatternへ明示的に対応付ける。Boardの原則カードを変更する場合もSchedule commandと変更範囲・例外への影響確認を通す。特定の回を選んでいない原則カードから「この回だけ」の日時を勝手に決めない。

関連Task/ノートの作成は[BUTTON_AUTOMATION_SPEC.md](BUTTON_AUTOMATION_SPEC.md)の共通actionで扱う。現在Recordや特定の回へのRelation、初期値・template・作成結果を開く処理を設定できる。本文のCRDT、Task due、定期予定の正本を二重化しない。

## 6. 論理モデルと責務の設計案

最終的なTypeScript/DB/operation schemaは後続の`DATA_MODEL.md`・`SYNC_SPEC.md`で定義する。次の名前は論理境界であり、PoCへの新規entity追加指示ではない。

| モデル | 主な責務 |
| --- | --- |
| ScheduleGroup | 予定群の名称、表示用分類、任意の適用期間/休止日。学期は一つの利用方法 |
| TimeSlotPreset | 名前付き時間帯と任意の日跨ぎ。時限・勤務帯等に利用。プリセット適用後の実時刻とは区別 |
| ScheduleSeries | 定期予定の名前・説明・場所等の共通情報。グループは任意 |
| RecurrencePattern | 曜日、間隔、基準週、適用期間、現地時刻・タイムゾーン。1系列に複数パターンを持てる |
| OccurrenceOverride | 元のパターン/開催日を指定した一回の取消または上書き |
| OneOffEvent | 通常の単発予定・補講等の追加開催。定期予定や元の回への関連は任意 |
| CalendarOccurrence | 規則・休止・例外・追加から表示範囲に生成するProjection。表示の再生成で新しい同期operationを発生させない |

開催時刻は現地の日付・時刻・タイムゾーンの意味を保持する。同期記録のcreatedAt/updatedAtは既存のUTC方針を維持する。Taskのdueはdate-onlyのままであり、Calendarの日時導入によってdatetimeへ変更しない。

- 予定のtimezoneと表示timezoneを分け、端末のtimezone変更で登録した毎週の現地時刻が変わらないようにする。表示timezoneが異なる場合は元のtimezoneを確認できるようにする。
- 日跨ぎ予定は開始日を元の回のキーに使い、表示上は翌日部分も参照できるようにする。
- 夏時間等で存在しない/複数の候補がある現地時刻は、黙って時刻をずらさず、検出と選択方針を定義してから実装する。ライブラリ・詳細解決規則は要決定。
- 取消された回も例外の参照先として識別できる。振替後の実開催日で検索でき、元の日付が表示範囲外でも振替先の予定を取りこぼさない。
- 表示用cacheは再生成可能とし、複数端末が同じ入力から同じ回・日時・取消状態を生成する。残った古いcacheを保存済みの正本にしない。

## 7. Local-first・同期・外部連携

定期予定・繰り返し・例外・追加の作成/更新/削除は構造化データとして保存し、entity更新とenqueueを同一local transactionで確定する。offlineでもCalendarを閲覧・編集でき、ACK再送やreconnectで追加の回が増えない。

- 同じ回への異なる上書き、取消と更新、原則設定と既存例外の変更等の競合規則を明示する。日時変更と取消を「削除対更新」のtombstone規則と混同しない。
- 一つの開催日時/繰り返し定義として整合性が必要な属性群は、atomicな値/操作の境界を検討する。field mergeで開始・終了や規則が無効にならないことを`SYNC_SPEC.md`で定義する。
- Google Calendar等はProvider Adapterを経由する。内蔵予定の利用はProviderへのログインに依存しない。
- 各回をCalendarに表示することと、外部へ予定を作成することは別機能とする。外部連携なしで勝手に外部予定を作らない。
- 外部連携の識別子対応、取消/例外の変換、双方向の正本、token管理、再送による重複防止は`INTEGRATION_SPEC.md`で確定する。

| CAL-04 | 10/12の回だけ取消/休講にする | 取消を識別でき、10/19等の他の回は維持。例外解除で原則へ戻る |
| CAL-05 | 10/12の回を10/13 10:40へ振替 | 振替先に有効な回が1件だけ表示され、元の回のキーと元の日時を保持 |

| CAL-07 | 学期外の日に補講、元の日付が表示週外の回を表示週へ振替 | 追加/振替先の日時検索で表示でき、学期全体を自動延長しない |
| CAL-08 | 時間帯プリセットを変更する | 既存予定の実時刻を黙って変更せず、一括適用時は対象と変化を確認できる |
| CAL-09 | 規則の曜日・期間を変更し、関連する例外に影響する | 例外を無断削除せず、変更範囲と例外の扱いを確認できる |
| CAL-10 | 複数予定が同時刻、土日開催、日跨ぎ、終了日なし | 重複や翌日部分を取りこぼさず、全将来分の展開をせず表示範囲を生成できる |
| CAL-11 | offlineで取消・振替・追加し、再起動後reconnect、同じ追加operationを再送 | 変更が保持され、他clientへ収束し、追加開催が重複しない |
| CAL-12 | 2端末で同じ回を別日時へ変更、または取消と更新を行う | Conflictと両候補を保持し、解決後に全端末が同じ回へ収束 |
| CAL-13 | 端末timezone/画面の週開始曜日を変更 | 予定の元の現地時刻と繰り返し規則を変更しない。日時表示の意味が分かる |
| CAL-14 | keyboard/タッチのみで登録・各回の取消/変更/追加・一覧切替を行う | Dragやhoverなしで全操作と日時・状態確認ができる |
| CAL-15 | 毎週月曜の予定を、11/02の回から火曜へ「この回以降」で変更する | 選択した回以降に新しい規則が適用され、起点より前の日時・取消・振替は変わらない。旧予定の終了と新規登録を手動で行う必要がない |
| CAL-16 | 定期予定の変更範囲を選ぶ | 「この回だけ／この回以降／全体」の3択と、影響する期間・既存例外を確認できる |
| CAL-17 | 毎週月曜を火曜へ変更し、変更範囲内に休講と振替がある | 対応する回への取消の引き継ぎ案と、日時を保持した振替の案を一覧で確認・修正できる。確認前には変更されない |
| CAL-18 | 曜日・期間の変更で例外の対応先がなくなる、または複数候補になる | 要確認として表示され、個別に扱いを選ぶまで確定しない。過去の範囲外の例外と独立した追加開催は変わらない |

これらは将来実装を検証する条件であり、現在のPoC試験のPass件数に含めない。

## 9. 次に確定する項目

- 初期リリースの提供時期、Calendarの各ビューと詳細操作の優先順位。
- 規則変更の期間分割、過去の開催情報、既存例外への影響を扱う最終モデル。
- 例外の引き継ぎ方針は4.2で決定済み。対応先の判定規則、要確認の詳細選択肢、競合時の再確認を具体化する。
- 月次・年次・ローテーション、複雑な休日/組織暦、終日・複数日予定の初期提供範囲。
- 夏時間の曖昧/存在しない時刻の解決方針、日時計算ライブラリ、表現・検索の契約。
- CSV/カレンダーファイル/大学システムからの取込み、外部同期、通知、出欠や成績管理。
- Pageノート・TaskとのRelation連携は汎用DB/共通Buttonの提供対象とする。Record/Pattern/Occurrenceへのbindingと提供時期は実装前に確定し、既存Page本文やTask期日の正本を変えない。

次工程は、要求と詳細案をリリース判断へ取り込み、`DATA_MODEL.md`・`SYNC_SPEC.md`・`INTEGRATION_SPEC.md`へ契約を落とすこと。PoC中の製品設計の整理と、PoCの検証順序を飛ばしてCalendarを実装することは区別する。
