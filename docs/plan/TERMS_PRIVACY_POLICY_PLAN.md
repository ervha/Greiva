# 日本向け利用規約・プライバシーポリシーの公開計画

2026-10-07追記：[アカウント保管境界・本文保護](ACCOUNT_PRIVACY_ENCRYPTION_SPEC.md)を台帳へ反映する。Supabase Authにメールが残り、Greiva APIがJWT claimsを一時受信し得る事実と、Greiva DB/ログにコピーしない方針を区別する。本文は通信/保存時暗号化を採用しserver復号を許容する設計。「運営者が読めない/E2EE/完全匿名」と説明しない。具体配備とbackup/ログ/保持を公開前に確認する。

2026-10-05。最初の公開対象は日本とする利用者回答を反映した製品設計。公開用の完成文面ではない。[任意改善データ](PRIVACY_TELEMETRY_SPEC.md)、[認証/認可](AUTHZ_SPEC.md)、[AI/音声](AI_ACTION_SPEC.md)と実装・運用の確定値を照合してから公開する。

## 1. 文書の精度を担保する方法

データフロー台帳を正本として、端末、API、Auth、collaboration、DB/storage、改善受信、CDN/proxy、backup、外部Providerごとに項目・目的・主体・送信/保管国・委託/第三者提供・保持・削除・アクセス権を記録する。設定の説明、ポリシー、運用設定、実際のnetwork/log出力を台帳に対応付ける。未実装の機能や未選定のProviderを利用中と記載しない。

「完全匿名」「すべて端末内」「本文を一切送らない」「停止で即時全削除」等を全機能へ広げない。任意改善データには本文を含めないが、利用者の端末間同期は本文等をサーバーへ送る。AIや音声の将来送信は別の許可範囲。end-to-end encryption未実装ならその保証も記載しない。

日本の個人情報保護委員会の通則編は利用目的、安全管理、委託先監督、公表事項、開示等の取扱いを定めている。実際のデータ分類と事業者の立場に基づき、該当する義務を公開前に点検する。[通則編](https://www.ppc.go.jp/personalinfo/legal/guidelines_tsusoku/)。識別子を乱数化しただけで匿名加工情報と断定しない。

日本向け提供でも国外のAuth/hosting/委託先を使う可能性がある。保管国だけで判断せず、外国事業者へのアクセス/提供の実態と契約を調査し、該当する同意・情報提供又は基準適合体制等の条件を確認する。通常の改善送信スイッチが国外提供に必要な説明を自動的に満たすとはしない。[外国にある第三者への提供編](https://www.ppc.go.jp/personalinfo/legal/guidelines_offshore/)。海外での提供は別の適用法/配布ゲートで追加判断する。

## 2. 利用規約の構成と確認

| 節 | 確定・照合する内容 |
| --- | --- |
| 運営者・適用範囲 | 正式名称、連絡先、対象サービス/配布物、個人/自端末同期の範囲、適用開始日 |
| 利用条件・アカウント | 利用年齢/未成年者、認証、端末管理、禁止行為、停止/異議申立ての手順 |
| ユーザーデータ | 権利の帰属、提供に必要な処理範囲、export、削除、退会、端末/同期/backupの実契約 |
| 提供範囲・料金 | 提供するplatform/機能、無料/有料の実条件、変更/終了の通知、課金を導入する場合の別途必要表示 |
| 保存・同期・障害 | 端末保存とサーバー同期の区別、未送信/復旧/競合、backup、サポートの実際の保証と制約 |
| 責任・紛争 | 責任制限、強行法規との関係、準拠法/裁判管轄等を確認。未決定の上限・管轄・免責を創作しない |
| 改定・同意 | 改定理由、告知/施行日、差分/旧版参照、再同意が必要な変更と適用手順 |

「いかなる場合も責任を負わない」のような包括免責をひな形からそのまま採用しない。消費者契約の責任免除等には無効となる条項があるため、公開文言を適用条件と照合する。[消費者庁・消費者契約法第8条の解説](https://www.caa.go.jp/policies/policy/consumer_system/consumer_contract_act/annotations/assets/consumer_system_cms203_230915_12.pdf)。ローカルのみの使用とaccount/sync開始の規約提示・同意時点は提供形態の確定後に定める。

## 3. プライバシーポリシーの構成

運営者、取得項目/方法、利用目的、認証/同期、任意改善データ、委託先/第三者/国外取扱い、安全管理、保持/削除/backup、開示・訂正・利用停止等の問い合わせ、未成年者、改定履歴を整理する。任意改善データはエラー・性能に限定し、初期OFF・端末ごとの同意・撤回方法を明記する。機能利用analyticsを記載/実装しない。

raw event、集計、同意台帳、必要なセキュリティログ、ユーザー内容、AI履歴/録音を別の保持目的とする。「送信停止」と「既受信データの削除依頼」を区別し、実際に可能な操作と反映時期を示す。削除対象、例外、backup/委託先への反映を曖昧にせず、日数未定のまま公開しない。

## 4. 変更管理・公開ゲート

文書ごとにdocument ID、版、施行日、対象アプリ/機能、review記録、diff、公開URL、同梱hashを管理する。規約同意と任意送信同意の台帳を分ける。必要な同意を記録する際は提示版、主体、サーバー確定時刻、同意操作の識別を保存し、外部送信範囲の拡大は旧同意で実行しない。

公開前に次を完了する。

1. 運営者/窓口、利用条件、対象機能、料金が実サービスと一致する。
2. 全データフロー・Provider・国・分類・委託契約・保持/削除・backupが確定し、ポリシーと照合されている。
3. schema/SDK/proxyを含む通信とログの検査、初期OFF/撤回/削除/目的変更の受入が済んでいる。
4. 日本向けの法的適用と公開文言を適切な専門確認に回し、未解決点を解消する。専門家確認を法律上常に必須と断定するものではなく、Greivaの公開品質ゲートとする。
5. 設定・初回提示・Web・同梱文書の版/リンクが一致し、offlineでも現配布版の文書と問い合わせ手順を読める。

運営者名/住所・窓口、利用年齢、料金、国外Provider/取扱国、保持期間、削除/退会・backup、規約同意の適用時点、責任/紛争条項は未確定。適用法の改定も公開時に再確認する。法的文書は初期提供全体のゲート、任意改善送信は独立した追加ゲートであり、収集条件未確定なら送信機能はOFF/未提供を維持する。
