# コミット・バージョン運用

2026-09-30のユーザー指定に基づき、確認済みのまとまった更新をコミットし、更新規模に応じたバージョンタグを付けてGitHubへ反映する。

## 1. 番号と更新規模

`VERSION`をリポジトリの開発チェックポイント番号とし、Gitのannotated tagを`vMAJOR.MINOR.PATCH`形式で付ける。[Semantic Versioning 2.0.0](https://semver.org/)の形式と互換性の考え方を参考に、Greivaでは次の運用とする。

| 区分 | 更新内容 | 例 |
| --- | --- | --- |
| PATCH | 互換性を維持した不具合修正、既存操作の細部改善、設計文書・ヘルプ・検証/開発環境の更新のみ | `0.1.0 -> 0.1.1` |
| MINOR | 実装済みの新機能、まとまった操作体験の追加、初期開発中の非互換な変更 | `0.1.3 -> 0.2.0` |
| MAJOR | 1.0以降で既存の公開契約との互換性を壊す変更 | `1.4.2 -> 2.0.0` |

複数の変更をまとめる場合は最も大きい区分を使う。MINOR更新時はPATCH、MAJOR更新時はMINOR/PATCHを0へ戻す。非互換な変更は件数や行数で判断せず、schema、同期契約、利用者のデータ・操作への影響を記録する。

設計した将来機能を実装済みの機能追加として数えない。開発中は`0.x.y`を使い、1.0への移行は本番の提供範囲・互換性・品質ゲートの判断に合わせて決める。ファイル数や文章量だけでMAJORへ上げない。

初回は既存の基盤/Editorと現在の設計をまとめた`v0.1.0`を基準にする。以前のコミットへ番号を推測して付け直さない。

## 2. コミット時の手順

1. 差分と変更区分を確認し、無関係な利用者の変更を含めない。
2. 変更に必要な検証を実行し、未検証項目を区別する。文書だけなら内容・リンク・差分を確認し、アプリ試験の新しい成功を主張しない。
3. `VERSION`と`CHANGELOG.md`を更新する。変更履歴には日付、実装/設計の区別、関連する検証・制約を残す。
4. 対象だけをstageし、確認済みの区切りをコミットする。メッセージは例として`docs: define candidate selection (v0.1.1)`のように番号を含める。
5. 同じコミットへannotated tagを付ける。タグ注釈に区分と具体的な変更を記載する。
6. 指定されたremote/branchへコミットとそのタグをpushし、remoteのタグが同じコミットを参照することを確認する。

pushでは対象のタグ名を指定し、無関係なローカルタグをまとめて送らない。公開済みのタグは移動・上書きせず、修正は次の番号で記録する。確認済みの過去のバージョンは履歴として保持する。

## 3. 開発チェックポイントと実行物

Gitタグはソースと設計の確認済みチェックポイントであり、インストーラの公開や全GateのPassを意味しない。今回の`v0.1.0`ではPoC Step 1–2の実装を含むが、Windows VMのnative/IME、保存・同期、Gate A/B/Cは未検証または未実装である。

既存PoCのpackage/Tauri/Cargoの仮番号`0.0.0`は、すでに生成した実行物の版と共に保持する。次にアプリのコードを変更してビルドする区切りでは、その実装チェックポイント番号へアプリ管理下のpackage/Tauri/Cargoの番号と対応lockfileを揃え、必要なDocker/VMの検証を行う。文書だけの変更で既存実行物を新しい版として扱わない。

個別設計書の`v0.x`はその文書の改訂番号として扱い、リポジトリのチェックポイント番号と一致させる必要はない。現在の版・Gitコミット・実際に検証した版を区別して証拠へ記録する。
